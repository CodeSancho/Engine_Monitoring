ABSTRACT

Mining and industrial engines operate under changing loads, and failures can interrupt production and create safety and maintenance costs. This project develops a prototype engine-monitoring application that streams multivariate sensor readings, detects anomalous operating windows, and presents fleet status and alerts through a browser dashboard. The system combines a React dashboard, a Node.js and Express API with Socket.IO, a Python Flask prediction service, and PostgreSQL hosted by Supabase. A CSV replay simulator supplies eight signals—temperature, rotational speed, fuel efficiency, three vibration axes, torque and power—to twenty virtual equipment identifiers. The live anomaly detector is an Isolation Forest trained on engineered features from the project’s ziya07 dataset. The model evaluation stored with the project reports precision 0.9500, recall 0.7308 and F1 0.8261 on a held-out test set containing normal windows and synthetic, physically motivated anomalies. Its confusion matrix contains 50 true negatives, 2 false positives, 14 false negatives and 38 true positives. These results apply to the stated synthetic evaluation and do not establish field performance on real haul trucks. A separate Random Forest model trained and tested on NASA C-MAPSS FD001 estimates remaining useful life (RUL); it achieves 10.19-cycle MAE versus a 37.50-cycle constant-mean baseline. This RUL demonstration is intentionally separate from live truck telemetry because the datasets describe different engine types and sensor systems. The application persists readings, predictions and alerts in Supabase and provides live fleet, chart, alert and manual-injection interfaces. The prototype demonstrates an end-to-end monitoring workflow, while sensor-domain mismatch, limited dataset provenance, absent field trials, and pending verification of the latest history endpoint remain important limitations.

Keywords: engine monitoring; predictive maintenance; anomaly detection; Isolation Forest; sensor telemetry

CHAPTER 1: INTRODUCTION

1.1 Background and Context

Engine condition monitoring uses measurements such as temperature, speed, vibration, torque and power to describe how equipment is operating. Maintenance teams can use trends and unusual combinations of measurements to identify conditions that merit inspection. Predictive-maintenance research commonly combines sensor acquisition, feature extraction and learning algorithms, but useful deployment depends on representative data and careful validation. An anomaly detector identifies observations that differ from a learned operating profile; it does not, on its own, identify a confirmed mechanical fault or prove that failure is imminent.

This project implements a browser-based monitoring prototype. The dashboard receives sensor events and model decisions from a backend, shows a fleet overview and per-engine graphs, and presents alerts. A simulator replays the local ziya07 CSV as a stream. The prototype therefore demonstrates an end-to-end software workflow, not a live connection to physical mining equipment.

1.2 Problem Statement

Operators and developers need a way to observe multiple engines, inspect incoming measurements, and see when a machine’s sensor window differs from the normal profile. A static dataset or offline notebook does not provide a continuously updated fleet view, persistent alert history or a practical way to explore model behaviour. At the same time, the project’s available data do not represent a verified fleet of haul-truck engines; claims of real-world fault prediction would exceed the evidence. The project addresses the software integration problem while making the simulation and model-domain limits explicit.

1.3 Project Aim

To design and implement a prototype real-time engine-monitoring application that streams sensor data, applies window-based anomaly detection, stores monitoring records, and presents fleet status, trends and alerts through a web dashboard.

1.4 Project Objectives

  1. Inspect and prepare the available engine sensor data and define window-level features.
  2. Train and evaluate an unsupervised anomaly detector on normal operating windows and separate synthetic anomaly windows.
  3. Build a backend service that simulates sensor telemetry, calls the prediction service and broadcasts readings, predictions and alerts.
  4. Build a dashboard for fleet status, live sensor graphs, alerts and controlled anomaly-injection demonstrations.
  5. Persist equipment, readings, predictions and alerts in PostgreSQL/Supabase and document installation and limitations.
  6. Train a separate RUL demonstration using NASA C-MAPSS FD001 without claiming it is valid for the live truck sensor stream.

1.5 Research Questions

  1. Can a prototype integrate a simulated multi-engine sensor stream with an unsupervised anomaly detector and a live dashboard?
  2. How does the trained detector perform on the project’s held-out set of normal and synthetic anomaly windows?
  3. How can the system communicate the distinction between a model anomaly score, a generated alert and a confirmed mechanical fault?

1.6 Scope of the Project

1.6.1 In Scope

The scope includes CSV-based sensor replay; eight sensor channels; a 30-reading live inference buffer; Isolation Forest anomaly classification; fleet and equipment views; charts; Socket.IO updates; alert acknowledgement; manual sensor-value injection for demonstration; database persistence; and an independent C-MAPSS RUL demonstration.

1.6.2 Out of Scope

Physical sensor installation, direct integration with a mine’s telemetry network, deployment to a production fleet, verified diagnosis of specific component failures, automatic maintenance scheduling, user authentication and role management, and use of C-MAPSS RUL estimates on ziya07 truck telemetry are outside the demonstrated scope.

1.7 Significance of the Project

The project brings model inference, streaming, dashboard visualization and database persistence into one prototype. It provides a practical base for evaluating the user workflow and exposes important engineering questions: whether anomalies are detected from meaningful data, how decisions should be surfaced, how to retain sensor history, and how to protect database credentials.

1.8 Limitations

The ziya07 dataset contains 1,000 rows at five-minute intervals and lacks a verified per-physical-engine identity. Twenty simulator identifiers are assigned separate contiguous portions of this one file; they are virtual streams, not twenty independent machines. The origin and licensing terms of the local ziya07 file are not documented in the repository. Evaluation anomalies are synthetically generated. The RUL model uses simulated turbofan data and is not mapped to truck sensors. Formal user testing and field validation are not documented. The database health endpoint has returned a successful connection response, but the newly added database-backed sensor-history endpoint returned HTTP 404 from the already-running backend process, indicating that the process needs to load the updated code before that feature can be considered operationally verified.

CHAPTER 2: LITERATURE REVIEW

2.1 Introduction

This chapter introduces condition monitoring, anomaly detection and remaining useful life estimation, then relates these concepts to the project’s two datasets and technical design.

2.2 Key Concepts and Theories

2.2.1 Condition monitoring and predictive maintenance

Condition monitoring observes measurements over time to assess equipment state. Predictive maintenance uses those observations to support intervention before a failure or unacceptable degradation. The quality of a monitoring decision depends on sensor coverage, operating context, data quality, model calibration and an appropriate response process. A statistical anomaly is evidence of difference from a reference distribution; it is not equivalent to fault diagnosis.

2.2.2 Isolation Forest

Isolation Forest detects unusual feature vectors by recursively partitioning data with random feature and split choices. Anomalous observations tend to be isolated in fewer partitioning steps than common observations. The project fits the model to feature vectors derived from windows treated as normal and classifies live windows with the fitted forest. The contamination setting controls the training decision threshold in the scikit-learn implementation; it should not be interpreted as the probability that an individual machine will fail [1, 2].

2.2.3 Window features and multivariate signals

Raw signals are summarized into means, standard deviations, minima, maxima, slopes and ranges. Such features represent operating level, variability and direction of change. Derived indicators combine selected signals, including vibration magnitude, power efficiency and thermal load per RPM. A multivariate detector may respond differently to a single altered signal than to a physically related combination. The model’s result is determined by the full engineered feature vector and its learned boundary, rather than by a universal fixed threshold for each sensor.

2.2.4 Remaining useful life

RUL is an estimate of time or operating cycles remaining before an asset reaches a defined end-of-life condition. It is supervised when historical run-to-failure sequences provide target RUL values. The NASA C-MAPSS data are simulated turbofan trajectories with a cycle-based progression. A model trained on them may support a benchmark demonstration, but transfer to another engine type requires validated feature correspondence and target-domain evidence.

2.3 Existing Systems and Related Work

Liu, Ting and Zhou introduced Isolation Forest as an isolation-based method for anomaly detection [1]. Its tree-based random partition strategy provides a computationally practical approach for tabular anomaly features. The scikit-learn implementation exposes both a score and a binary inlier/outlier prediction; the score and class are distinct outputs [2].

Saxena and colleagues described damage propagation modelling for aircraft-engine run-to-failure simulation, and NASA’s C-MAPSS materials document a simulated turbofan environment intended for engine-control and prognostics work [3, 4]. The C-MAPSS benchmark supports RUL experiments on consistent simulated engine trajectories. It does not supply a validated mapping to the project’s eight ziya07 signals.

Industrial monitoring systems typically combine data acquisition, processing, model inference and an operator-facing interface. This project adopts that architectural pattern at prototype scale: the simulator substitutes for hardware acquisition, Flask provides inference, and the React dashboard provides visualization and alert interaction.

The practical gap addressed here is an integrated, inspectable prototype that connects an anomaly model to a real-time fleet interface and persistent alert records while distinguishing simulation from physical deployment. The repository does not establish that this is the first such system or provide a systematic review sufficient to claim a broad academic research gap. The project’s defensible contribution is an implementation and evaluation exercise using its stated data and a transparent account of domain limits.

2.6 Conceptual Framework

The system follows an input–processing–output workflow. Inputs are timestamped multivariate readings. Processing validates and buffers readings, computes a feature vector and applies the Isolation Forest. Outputs are a model score and class, an alert when the class is anomalous, a fleet status update, and stored records. A human operator reviews the alert and acknowledges it; the prototype does not autonomously authorize maintenance.

CHAPTER 3: METHODOLOGY

3.1 Introduction

The project used an applied software-development approach supported by offline data preparation, model training and held-out evaluation. A simulator supplied the live application with repeatable readings because no physical fleet connection is present in the repository.

3.2 Research and Development Approach

Development was iterative: inspect data and existing code; prepare window features; train and evaluate models; implement a Flask predictor; integrate it with a Node.js simulator and Socket.IO; create React views; and add PostgreSQL persistence. The work is a prototype study rather than a controlled field trial. Reproducibility depends on the tracked datasets, model artifacts, feature-column files and configuration.

3.3 Requirements and Data Collection

The primary application dataset is data/raw/engine_failure_dataset.csv, a local 1,000-row file with timestamps, eight numeric signals, Fault_Condition and Operational_Mode. Rows are five minutes apart. The repository does not record the dataset publisher, collection site or license; those details should be supplied by the project owner before submission. The file is treated as a provided dataset and is not represented as raw data collected by the student.

The separate data/raw/train_FD001.txt file contains NASA C-MAPSS FD001 training trajectories. The preprocessor identifies engine identifiers and cycles, selects 14 sensor columns, computes end-of-life cycle distance and caps the RUL target at 125 cycles. No human participants or personally identifiable information are documented.

3.4 System Architecture and Workflow

The live workflow is: CSV row → simulator mapping → Socket.IO sensor event and database insert → rolling buffer → HTTP request to Flask → engineered window vector → Isolation Forest result → fleet state, Socket.IO prediction and optional alert → Supabase prediction/alert insert → dashboard display.

3.7 Evaluation Method

The Isolation Forest evaluation splits normal windows into training, validation and test subsets using a fixed random seed. Training uses 60% of normal windows; validation and testing each use 20%. Synthetic anomalies are generated independently for validation and test, with physically motivated bundles for bearing wear (three vibration axes), overheat (temperature and fuel efficiency), and mechanical binding (torque and RPM). Contamination candidates are 0.01, 0.02, 0.03 and 0.05, selected with validation checks that constrain false alarms on normal windows. Final metrics are precision, recall, F1 and a confusion matrix. The RUL model uses an 80/20 engine-level split and reports MAE and RMSE against a constant-mean baseline.

4.7 Database and Data Design

The PostgreSQL migration defines four related tables. equipment stores the stable equipment identifier and display name. sensor_readings stores a timestamp, typed sensor columns and a JSONB copy of the complete mapped reading. predictions stores severity, model score, message, feature snapshot and top anomalous features. alerts stores the same decision context plus acknowledgement state and time. Foreign keys associate records with equipment, and indexes support recent readings and alert lookup by equipment/time.

4.8 Interface and Interaction Design

The dashboard separates fleet overview, individual engine detail, alerts, model information and anomaly injection. Sensor graphs use a bounded recent history. The injector displays dataset ranges and standard-deviation distance, then waits for a model event before reporting whether an alert was generated. The score is an anomaly score and is not presented as a calibrated failure probability.

4.9 Algorithms, Models and Technical Design

For each live window, eight sensor streams each contribute six statistics (mean, standard deviation, minimum, maximum, slope and range). Three derived features produce a 51-feature vector. The stored Isolation Forest has 200 trees, contamination 0.05 and a fixed seed. The RUL demo uses a Random Forest regressor with 200 trees, an 87-feature vector and capped target RUL of 125 cycles. These models serve different data and prediction tasks.

4.10 Chapter Summary

The design separates the dashboard, orchestration API, inference service and database. It preserves a clear boundary between truck-like simulated telemetry and the turbofan RUL demonstration.

CHAPTER 5: IMPLEMENTATION AND DEVELOPMENT

5.1 Introduction

This chapter summarizes the implemented modules and their integration.

5.2 Development Environment

The repository contains a Vite-based React dashboard, an Express backend, a Flask service, local datasets and saved model artifacts. Dockerfiles and a Docker Compose configuration describe a three-service deployment with Nginx serving the built dashboard. Runtime secrets are supplied through backend environment variables; the example file contains placeholders rather than credentials.

5.3 System Components and Modules

  • Simulator service: reads the CSV, maps raw columns into display sensor names, assigns each virtual engine a non-overlapping segment and emits readings at a configured interval.
  • Prediction service: extracts window features, applies the saved scaler and Isolation Forest, and returns score, class and feature summaries.
  • REST and Socket.IO API: exposes fleet and alert routes, anomaly injection and streaming events.
  • Dashboard: renders fleet cards, engine charts, alert list, model demo and injector interface.
  • Database service: uses the Node pg pool and a server-side Supabase connection URI to write readings, model predictions and alerts; it also reads alert state and recent sensor history.
  • RUL demonstration: serves selected CMAPSS units and cycles through predictions separately from live monitoring.

5.4 Key Implementation Details

The simulator configures twenty virtual engines by default and divides the 1,000 source rows into separate contiguous segments. It fills a rolling 30-reading buffer and calls the model once a full window exists. Database operations are asynchronous and log persistence failures without halting live stream processing. The initial schema enables RLS on all four app tables. Health checking executes a lightweight database query and reports configured/connected state. The chart-history integration adds a backend query for the most recent 60 readings and merges the returned values with readings received over Socket.IO.

The manual injector sets explicitly selected values on all readings currently in the selected simulator buffer. It does not directly create an alert. The next model response determines whether the window is classified as anomalous. Its interface now reports the value’s distance from the dataset mean and explains why a deviation may not cross the model decision boundary.

5.5 Integration

Socket.IO carries sensor_reading, prediction, new_alert and acknowledgement events. The backend calls Flask over HTTP. The frontend requests fleet and alert state over REST and listens for live events. The backend connects to PostgreSQL using DATABASE_URL or SUPABASE_DB_URL. A health response supplied during project work reported configured: true and connected: true on 11 October 2026.

5.6 Challenges and Solutions

  • Feature drift: explicit saved feature-column ordering and startup assertions reduce model/code mismatch.
  • Inappropriate labels: the evaluation avoids treating Fault_Condition as ground truth for synthetic test anomalies; the label still contributes to selecting nominal training windows, so its validity remains a limitation.
  • Domain mismatch: live truck-like telemetry and turbofan RUL are separated rather than using fabricated sensor mappings.
  • Database DNS setup: the direct connection hostname did not resolve; using the Supabase session-pooler URI resolved connectivity, confirmed by the health response.
  • Live graph persistence: browser-only history would reset after refresh; a database history endpoint was added, but the process currently running on port 3000 returned HTTP 404 until restarted with updated code.
  • Alert interpretation: manual value changes did not guarantee a model anomaly; the UI was updated to show deviations and the next actual model classification.

CHAPTER 7: DISCUSSION

7.1 Introduction

This chapter interprets the model metrics and software integration against the project aim and evidence limits.

7.2 Interpretation of Findings

The prototype shows that a simulator, inference API, web socket stream, dashboard and PostgreSQL store can be integrated into one monitoring workflow. The model’s 0.95 precision indicates that most positive classifications in this particular test mix correspond to synthetic anomalies, while 0.7308 recall shows that nearly three in ten injected test windows were missed. Because the evaluation anomalies are created by the same project’s specified perturbation patterns, these metrics should be read as internal validation, not generalization to real equipment faults.

The injector experience also illustrates a key human-factors issue. “Outside the typical range” and “classified anomalous” are not synonymous. The Isolation Forest evaluates a complete feature vector with derived statistics, so changing one sensor can move the observation without crossing the detector boundary. The application now distinguishes deviation from the model’s actual next decision.

The separate RUL experiment is useful for demonstrating a supervised prognostics workflow and model evaluation. Its target and sensors are specific to C-MAPSS turbofan simulation; presenting those estimates as remaining operating hours for mining engines would be misleading.

7.3 Comparison with Existing Work

The Isolation Forest method follows the principle that anomalies can be isolated with shorter random-tree paths [1, 2]. The project applies it to engineered multi-sensor windows rather than raw single points. The RUL workflow uses C-MAPSS, a NASA-developed simulation environment [3, 4]. The prototype’s contribution lies in software integration and transparent separation of domains; it does not claim a novel anomaly algorithm or a new RUL benchmark result.

7.4 Contributions of the Project

  • A modular prototype connecting sensor replay, model inference, live dashboard updates and persistence.
  • A reproducible feature-based Isolation Forest training and evaluation pipeline with validation/test separation and synthetic raw-level perturbations.
  • A separate CMAPSS RUL model and demonstration that avoids presenting cross-domain estimates as live equipment predictions.
  • A manual injection workflow that reports model outcomes and communicates that dataset deviation is not a deterministic alert threshold.
  • A PostgreSQL schema for equipment, readings, predictions and alerts.

7.5 Limitations and Implications

The first limitation is ecological validity: the monitor replays one small dataset across virtual identifiers, so the simulator cannot capture independent machine behaviour or real operational context. The second is label and provenance uncertainty: the local file’s publisher and license are absent, and Fault_Condition is not a reliable fault ground truth in the project’s evaluation rationale. Third, the synthetic anomalies reflect chosen bundles and severities; unrepresented failure modes may be missed. Fourth, no field deployment or user study establishes operational benefit. Fifth, wildcard CORS and missing authentication limit safe exposure. Sixth, frequent sensor writes will need batching, retention and partitioning decisions for longer running or larger fleets. Finally, the live engine anomaly model is not calibrated to failure probabilities; its displayed score should remain a model score.

7.6 Chapter Summary

The project meets a prototype integration goal and reports transparent benchmark results. Its present evidence justifies further controlled testing, not production maintenance decisions.

No objective establishes production readiness or real-fleet predictive performance.

8.5 Recommendations

  1. Document and verify the provenance, collection context and license of the ziya07 dataset.
  2. Acquire representative, timestamped data from actual target engines, including operating conditions and independently verified maintenance/fault outcomes.
  3. Evaluate with machine-level and time-ordered splits that prevent leakage, and report confidence intervals and false alarms per operating time.
  4. Review whether nominal windows can be defined without relying on questionable Fault_Condition labels.
  5. Restart the backend with the latest code and verify that readings appear in Supabase, the history API returns them, and alerts persist and acknowledge correctly.
  6. Protect the API with authentication, restrictive CORS, rate limits, input validation and least-privilege database access before deployment.
  7. Batch or queue sensor inserts and define retention/partitioning once expected event rates and operating periods are known.
  8. Conduct operator usability evaluation and record task completion, alert comprehension and false-alarm tolerance.
  9. Keep the C-MAPSS RUL feature explicitly separated until a validated target-domain RUL dataset and model are available.

8.6 Future Work

Future work could include edge-device integration, sensor-quality checks, concept-drift monitoring, calibrated alert thresholds, explainability tied to validated components, user roles, audit trails, notification delivery, model versioning, continuous evaluation and a domain-specific prognostics model trained on real engine histories.

APPENDIX B: USER MANUAL AND INSTALLATION GUIDE

B.1 Prerequisites

Install a supported Node.js runtime, Python with the project dependencies, Docker Desktop if using Compose, and access to a Supabase project. Use the supplied model artifacts and data files. Do not place database credentials in dashboard variables or commit them to source control.

B.2 Database setup

  1. Open the Supabase project and copy the PostgreSQL connection string from its Connect panel. For local IPv4-only networks, choose the session pooler URI and retain SSL requirements.
  2. Set DATABASE_URL in backend/.env. Keep it quoted if the value contains characters parsed specially by dotenv; URL-encode reserved password characters.
  3. Run backend/db/001_initial_schema.sql in the Supabase SQL Editor.
  4. Start the backend and open /api/health. Confirm the database field reports configured: true and connected: true.

B.3 Run locally

  1. Start the Flask service on port 5001 with the saved models and processed result files available.
  2. From backend, install dependencies if needed and run npm start. Set FLASK_URL, DATA_PATH, PORT and database variables.
  3. From dashboard, install dependencies if needed and run npm run dev, configuring VITE_API_URL when the API is not on localhost:3000.
  4. Open the dashboard, wait for the WebSocket connection and simulator warm-up, then use Fleet, Alerts, Model Info and Manual Anomaly Injection views.

B.4 Interpreting the injector

Select an engine, choose one or more sensors, enter the exact values and submit. The interface reports distance from the dataset average. After the next model event, it reports NORMAL or an alert. A deviation is not a guaranteed fault or alert; the model evaluates the full window.

B.5 Data review

Use the Supabase Table Editor to inspect equipment, sensor_readings, predictions and alerts. Confirm fresh timestamps and acknowledged state. If the graph-history API returns 404, restart the Node backend so it loads the current route before testing again.

C.3 Event flow

The Node simulator emits a sensor event, stores the reading, adds it to an engine buffer and calls the Python predictor for a full window. The predictor response updates fleet state, is stored, and is broadcast to the browser. A non-NORMAL response creates an alert that is stored and broadcast.
